# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

WhatsOn is a personal "what's on" dashboard for Southampton, UK (weather, tides, cruise ships, roadworks, football fixtures, theatre, pub live music, city events, plus a few non-local favourites like TV/radio and sport). The original brief is in `docs/brief.md`.

## Architecture

Static site, no server, no database engine:

```
GitHub Actions (cron)  →  fetch script  →  data/current/*.json + data/history/*.csv  →  git commit/push
                                                              │
                                                              ▼
                                          GitHub Pages serves repo statically
                                                              │
                                                              ▼
                                    index.html / <feed>.html + app.js fetch()es the JSON, renders it
```

Each category (a "feed") is fully independent: its own fetch script, its own scheduled GitHub Actions workflow, its own JSON/CSV output, its own detail page. A broken or rate-limited feed can't affect the others. There is no build step and no client-side framework — plain HTML/CSS/JS.

### Adding a new feed

Follow the pattern of existing feeds (check `scripts/`, `.github/workflows/`, and `data/current/` for the latest example):

1. `scripts/fetch_<feed>.py` — calls the external source, normalizes the result, overwrites `data/current/<feed>.json`, appends a dated row to `data/history/<feed>.csv` if historical comparison is useful, exits non-zero on failure (no silent stale data). Use the shared helpers in `scripts/_common.py` rather than re-implementing them: `REPO_ROOT`, `USER_AGENT`, `fetch_text(url)` (GET with the shared UA + `raise_for_status`, returns `.text`), `write_json(path, data)`, and `run(main, label)` (wraps `main()` in the standard try/except → stderr + `sys.exit(1)` pattern — the whole `if __name__ == "__main__":` block should just be `run(main, "<feed>")`).
2. `.github/workflows/fetch-<feed>.yml` — `schedule:` (cadence appropriate to how often the source actually changes) + `workflow_dispatch:` (for manual testing), `permissions: contents: write`, installs `requirements.txt`, runs the script, commits+pushes only if `data/` changed.
3. An overview card on `index.html` (a real `<a>` link, not a clickable `<div>`, whose visible/accessible text includes the current summary value) linking to `<feed>.html`.
4. `<feed>.html` — a detail page sharing the same header/`styles.css`, with a "Back to dashboard" link before its content.
5. A registry entry + render function in `assets/app.js` (fetch path, overview summary renderer, detail renderer). Reuse the existing shared helpers rather than re-duplicating: `groupByLocalDate`/`localDateKey`/`formatDayHeading`/`formatTime` for date handling, and `pushHeading(elements, text)` / `pushFetchedAt(elements, data, sourceName)` for the two small pieces every `renderDetail` needs (a day/section `<h2>`, and the trailing "Data fetched ... from ..." paragraph).

Secrets (API keys) go in GitHub repo secrets, injected as env vars only inside that feed's workflow — never exposed client-side, since GitHub Pages content is public.

### Accessibility (required, not optional)

The dashboard is built and verified against **NVDA + Firefox** (the maintainer's daily setup), with a Chrome spot-check per feed. Practical implications for any frontend change:

- Real semantic HTML only — `<header>`/`<nav>`/`<main>`, one `<h1>` per page, proper heading hierarchy. No custom interactive widgets or hand-rolled ARIA. No skip-to-content link — the maintainer navigates by heading (NVDA's `H` key) rather than relying on one.
- **Never make a heading itself a link.** A card is a heading (plain text) followed by its content, with any link (e.g. "View weather details") as its own element within that content — not wrapping the whole card/heading in an `<a>`. Overview cards are still real `<a>` elements for the actual link, never `<div onclick>`.
- Client-side data loading needs a visible loading state and a *scoped* `aria-live="polite"` region around just the content that updates (not the whole page).
- Tabular data (tide times, hourly forecasts, ship listings) uses real `<table>`/`<caption>`/`<th scope>` markup, not div-grids — NVDA's table navigation depends on it.
- Dates/times use `<time datetime="...">`.
- Verify with an actual NVDA+Firefox pass (heading/landmark nav, table nav, live-region announcement) before calling a feed done — not just a visual check.

## Running locally

No build step. Serve the repo root and open it:

```
python -m http.server
```

Fetch scripts can be run directly to regenerate data files before testing the frontend against them:

```
pip install -r requirements.txt
python scripts/fetch_weather.py
```

## Repo layout

```
index.html               # overview dashboard — one summary card/link per live category
<feed>.html               # one detail page per category (e.g. weather.html)
assets/
  app.js                  # feed registry + render functions
  styles.css
data/
  current/<feed>.json     # latest snapshot per feed, read by the frontend
  history/<feed>.csv      # append-only history per feed, where useful
scripts/
  _common.py              # shared fetch-script helpers — REPO_ROOT, USER_AGENT, fetch_text(), write_json(), run()
  fetch_<feed>.py          # one fetch script per feed
.github/workflows/fetch-<feed>.yml   # one scheduled workflow per feed
docs/brief.md             # original project brief
requirements.txt          # Python deps for the fetch scripts
```

## Build order

Feeds are built one at a time, fully shipped (script + workflow + page + NVDA-verified) before the next starts. Current order: weather → tides → cruise ships → city events → TV/radio new series → football fixtures → Southampton Airport, then further categories as they're scoped. Check `data/current/` and `.github/workflows/` for what's actually live versus still planned — this file won't stay in sync with day-to-day progress.

Several feeds rely on undocumented endpoints/scraping rather than official APIs, all a deliberate judgment call by the maintainer — don't "fix" fragility here by working around it technically, just expect occasional maintenance if the source changes:

- **Tides** (`scripts/fetch_tides.py`) calls EasyTide's own internal `Home/GetPredictionData` endpoint (reverse-engineered from its frontend JS) rather than the official ADMIRALTY UK Tidal API, because that API's developer-portal signup was too cumbersome. No API key needed.
- **Cruise ships** (`scripts/fetch_cruise_ships.py`) reads ABP Southampton VTS's public XML feed at `/xml/sotcruiseship.xml` — the same feed their own "Cruise Ship Schedule" page renders client-side via XSLT (`/xsl/sotcruiseship.xsl`). Not a documented API, but it's the actual data ABP serves to any visitor's browser, so a step more solid than scraping rendered HTML. Extends months ahead; capped to a 14-day window in the script (`LOOKAHEAD_DAYS`) to keep the page a manageable size — raise that constant if more lookahead is ever wanted.
- **City events** (`scripts/fetch_city_events.py`) merges three independent, undocumented sources into one deduplicated list, scraped with `beautifulsoup4`. hellosouthampton.co.uk's "What's On" page — chosen specifically *instead of* the user's original idea of scraping `facebook.com/hellosoton`, since Facebook's Terms of Service explicitly prohibit automated access (a firm line, unlike the sources here) and its real event data sits behind a login wall anyway — is a normal WordPress site (`robots.txt` only disallows `/wp-admin/`) with clean server-rendered event cards; it server-renders ~45 upcoming events (~a month out), more behind a JS "Load More" button not pursued. The University of Southampton's own events calendar (`events.soton.ac.uk`) was added after this feed missed the British Science Festival (hosted at the University, September 2026) — despite its JS-driven look, the whole year's events are actually server-rendered straight into the page (JS just filters/hides the same markup), so one GET returns everything; most entries link to their own external booking page (Eventbrite, Zoom, a department site), and the handful with no specific start time (exhibitions, multi-day courses) are skipped. Visit Southampton's "Top events of 2026" article (`visitsouthampton.co.uk/events/annual-events/`) is the third source, added because it's the one place confirmed to actually list the British Science Festival — Eventbrite was ruled out entirely (its public event-search API was deprecated; only per-organiser OAuth or a distribution-partner program remain) and Skiddle was ruled out for this specific gap (it has a real free API, but the festival books through TicketSolve, a platform Skiddle's promoter-submitted inventory has no visibility into). Visit Southampton also runs a proper events database (988 individual event pages per its sitemap, browsable at `/events/`), but that listing's plain HTML only ever surfaced a handful of near-term events with no pagination/API call visible in the markup, so the annual-events article was used instead — it's editorial prose, not structured data (title/date/venue squashed into one comma-separated string per event under a month/year heading, no machine-readable date), parsed with a regex against irregular hyphen/en-dash date ranges and a year inferred from the section heading. More fragile than the other two sources, and it only covers ~20 flagship annual events rather than day-to-day listings, but it's what actually closes the gap. Its entries carry a date but no specific time (`"all_day": true` in the JSON, rendered as "All day" instead of a clock time). Deliberately unfiltered by category — includes anything the sources list (festivals, gigs, markets, family events, lectures, and any sports fixtures that happen to be advertised too) rather than building category-guessing logic. When the same event appears from more than one source on the same day, `dedupe()` keeps only one copy — titles are normalized (lowercased, years/punctuation stripped) and treated as the same event if every word of the shorter title appears in the longer one (the pattern real duplicates like "Southampton Pride" vs "Southampton Pride 2026" actually follow), keeping the copy from the highest-priority source: Visit Southampton > University > hellosouthampton. Each source is fetched independently and a broken one doesn't blank out the rest (same `safe_fetch`-style isolation as `fetch_tv_radio.py`).
- **TV & radio new series** (`scripts/fetch_tv_radio.py`) combines three undocumented sources for one feed: BBC One/Two/Three/Four use BBC iPlayer's own internal schedule API (`ibl.api.bbci.co.uk/ibl/v1/channels/{id}/schedule/{date}`) — the same data iPlayer's own schedule view renders, keyed by an arbitrary-but-stable English region id since regional opt-outs don't affect series/episode metadata. BBC Radio 4 and BBC World Service use the JSON API BBC Sounds' own Next.js schedule page calls client-side (`rms.api.bbc.co.uk/v2/experience/inline/schedules/{station}/{date}`, discovered via that page's embedded `__NEXT_DATA__` — station ids are `bbc_radio_fourfm` and `bbc_world_service`; note `bbc_radio_four` without the `fm` 404s). Unlike the BBC TV source, this radio endpoint exposes no repeat/rerun flag, so a same-week repeat of a series' first episode could occasionally register as a false "new series" — an accepted gap, not a bug, reflected in those channels' `confidence: "medium"`. World Service specifically is mostly rolling news/strand programming without "Series N" numbering, so it will often legitimately show no matches at all. ITV1 has no BBC-style endpoint at all, so it falls back to TVmaze's public GB schedule (`api.tvmaze.com/schedule?country=GB&date={date}`) filtered to network `"ITV1"` — structurally the weakest signal (no rerun/text cue, just "episode number 1"), hence `confidence: "low"` with a caveat shown on its detail-page section. "New series starting" itself is a heuristic in all cases (subtitle/episode-number pattern matching, tuned against real schedule data but not a guarantee) — see the docstring and comments in `fetch_tv_radio.py` for the exact rules. Each of the 7 channels is fetched independently and failures are isolated per-channel (unlike every other fetch script here, where any exception fails the whole run) so one source breaking doesn't blank out the rest.
- **Football fixtures** (`scripts/fetch_football.py`) covers Southampton FC, AFC Bournemouth and Eastleigh FC via ESPN's public but undocumented soccer scoreboard API (`site.api.espn.com/apis/site/v2/sports/soccer/{league}/scoreboard?dates=...`) — the same data ESPN's own site/app renders. Chosen over the alternatives tried first: TheSportsDB's free key only ever returns a single next fixture per team (full-season access needs a paid Patreon key), and the clubs' own official sites don't share a common scrapeable template (saintsfc.co.uk didn't even respond to a plain request while evaluating this). Each club's fixtures are assembled by querying its relevant ESPN league slug(s) — `eng.1` (Premier League) for Bournemouth, `eng.2` (Championship) for Southampton, `eng.5` (National League) for Eastleigh — plus the shared cup slugs `eng.fa` (FA Cup) and `eng.league_cup` (EFL/Carabao Cup), filtered to events involving one of the three teams. The scoreboard endpoint caps at ~100 events per request; the whole "current season" window (1 August–31 July, see below) can exceed that for the National League even at `CHUNK_DAYS`=21, so each competition is queried in date-range chunks and merged — this means noticeably more requests per run than a simple lookahead window would (season span ÷ 21 days × 5 competitions), accepted since most cup chunks return zero events until that round is actually scheduled. No ESPN slug was found for the FA Trophy (the actual non-League cup Eastleigh enters, distinct from the League One/Two "EFL Trophy") — those fixtures are a known, accepted gap. Team-to-league mapping is a hardcoded list in the script (`CLUBS`/`CLUB_LEAGUE_SLUG`/`COMPETITIONS`), so a club's promotion/relegation between seasons needs a manual update, same maintenance tradeoff as this project's other undocumented sources. The fetch window itself is computed, not fixed: "current season" is 1 August of the season-start year through 31 July the following year, where the season-start year is this year if today is July–December else last year — this both scopes `past_results` to the right season and gives the maintainer's requested 1 July flip between "showing last season's results" and "showing next season's fixtures" for free, with no separate date-branching needed in the frontend. League position/points come from a second, separately-discovered undocumented endpoint — `site.api.espn.com/apis/v2/sports/soccer/{league}/standings` (note `/apis/v2/`, not `/apis/site/v2/`, which returns an empty object for soccer standings; confirmed live 2026-08-23) — parsed as `children[].standings.entries[].stats[]` (a list of `{name, value}` pairs; `rank` and `points` are the ones used). `fetch_standings()` is wrapped and isolated (same `safe_fetch`-style philosophy as `fetch_airport.py`'s adsb.lol lookups): if ESPN changes this shape or the call fails, a club's `league.position`/`league.points` just come back `null` rather than failing the run. Cup status (`in_progress` / `knocked_out` / `through`) is a heuristic, not a flag ESPN provides: a club with an upcoming fixture in a cup is `in_progress`; otherwise its most recent result in that competition decides it — a loss means `knocked_out`, a win/draw with no next fixture yet scheduled means `through` (progressed, ESPN just hasn't published the next round yet) rather than incorrectly reporting them as knocked out — the same early-rounds-scheduling lag already noted above for Eastleigh's cup fixtures.
- **Southampton Airport** (`scripts/fetch_airport.py`) reads `southamptonairport.com/Umbraco/api/FlightsApi/RetrieveFlights` — an undocumented Umbraco CMS endpoint the airport's own live arrivals/departures board calls client-side. Plain GET, no auth; query parameters (date filters etc.) are accepted but ignored server-side — it always returns whatever's currently on the live board (today's flights, occasionally spilling into the next day's first departure or two). The API exposes no aircraft registration/tail number, so "which physical aircraft flies which flight" can't be confirmed from this source and no free alternative was found that reliably fills that gap either. Instead, `match_rotations()` infers same-aircraft turnarounds heuristically: for each arrival, the next not-yet-claimed departure to the same place, in time order, is treated as that aircraft heading back out — modelling how Southampton's short regional routes are actually flown (one aircraft shuttling a route back and forth all day, usually a 30–40 minute turnaround). Verified against live data on 2026-08-19: correctly paired all 11 same-day turnarounds and one overnight turnaround (a Newcastle arrival matched to the following morning's departure), while correctly leaving two genuinely unpaired departures unmatched. Presented on the detail page as an inferred pairing, not a confirmed one. Where the board's own status text signals a flight is actually in the air — anything but `"Scheduled"` or `"Arrived ..."` on an arrival (the board uses several in-flight states, not just one — `"Expected HH:MM"`, `"On Approach"`, etc.), or `"Airborne ..."` on a departure — `match_flight_position()` also looks up a live distance-from-airport via adsb.lol's free, no-key ADS-B tracker, since the flight board itself carries no live position. This can't be done by looking up the flight's own callsign directly: verified live against adsb.lol, most of this board's airlines (easyJet, Loganair, Aurigny) broadcast a semi-random per-rotation ADS-B callsign with no fixed relationship to their public flight number (e.g. easyJet's `"EZY416"` on the board was seen broadcasting live as `"EZY17DR"` — the two have nothing in common), so guessing an exact callsign to query `v2/callsign/{callsign}` with essentially never works. What IS reliable is the callsign's 3-letter airline prefix (`AIRLINE_ICAO_PREFIXES`, e.g. Loganair broadcasts under `LOG` regardless of what the flight number says) — so instead the script makes one `v2/lat/{lat}/lon/{lon}/dist/250` call per fetch (250 nautical miles being the API's own cap, centred on the airport, covering most routes close to the Southampton end of the flight — Faro is too far to ever be caught this way, an accepted gap) and, per in-progress flight, filters that shared snapshot to aircraft broadcasting the right airline prefix. Airline prefix and route bearing (`DESTINATION_COORDS`) alone weren't a fine enough filter in practice: KLM and Aer Lingus mainline traffic have enough aircraft in UK/European airspace at once that some coincidentally share a similar bearing from Southampton, and two of this board's own routes (Aurigny's Guernsey and Alderney) leave Southampton only a few degrees apart, so bearing-only matching frequently found either zero or several plausible aircraft and had to give up. `estimate_progress_distance()` adds a second, independent signal: roughly how far into its route a flight should be by now, from its remaining time to the board's live ETA (arrivals) or its actual parsed-from-status takeoff time (`"Airborne HH:MM"` — departures) against one flat assumed cruise speed (`ASSUMED_CRUISE_MPH`, chosen to land close to this board's real block times, e.g. ~30min for the ~125mi Jersey hop). A departure whose estimated progress already reaches the destination is treated as landed and skipped outright — southamptonairport.com never updates a departure's status past `"Airborne"` even long after the aircraft has actually landed, so without this cutoff every long-since-landed flight would keep being (mis)attempted every run. All of this depends on reading the board's timestamps in the right clock: despite carrying no timezone suffix, they're UK local time (BST/GMT), not UTC — confirmed live on 2026-08-23 when an `"Airborne 12:40"` status turned up in a 12:04 UTC fetch (only sane if that 12:40 is local; as UTC it would be in the future). Comparing against UTC "now" instead of `Europe/London` (via `zoneinfo`, so it tracks the BST/GMT switch automatically rather than a hardcoded offset) silently broke every departure estimate for about an hour a day: a takeoff misread as UTC reads as further in the future than reality, elapsed time clamps to ~0, and the search collapses to "still at the gate" — which is exactly what happened during development, producing two matches (for `EZY416` and `LM322`) that looked clean but were later confirmed wrong once the clock was fixed and re-checked against a real flight (`EZY142`, independently cross-checked against FlightAware by hand) tracked end-to-end. `match_flight_position()` then requires a candidate to be both on the right bearing *and* roughly the right distance out for elapsed time, and — unlike the bearing-only first pass — takes the single best-scoring candidate rather than bailing out on any ambiguity, since by this point genuine ambiguity is rare. One further accepted gap: Aer Lingus's Southampton routes are actually operated by Emerald Airlines under an "Aer Lingus Regional" codeshare, which may broadcast a different airline prefix entirely (unconfirmed), so those flights may never get a live distance; likewise Aurigny's small Channel Islands turboprops are sometimes simply invisible to adsb.lol in the minutes right after takeoff (low altitude, weak signal), a genuine coverage gap rather than a matching failure. The nearby-aircraft lookup is isolated from the rest of the run (same `safe_fetch`-style philosophy as `fetch_tv_radio.py`), so an adsb.lol outage just means no flight gets a live distance that run rather than failing the whole fetch.

- **Astronomy — orbital events** (`scripts/fetch_astronomy.py`) computes, rather than fetches, the next Moon perigee/apogee, next Earth perihelion/aphelion, and next solstice/equinox — sunrisesunset.io (the feed's main source) doesn't carry these, and no free API covering all three was found. Computed via Skyfield against NASA JPL's DE421 ephemeris kernel instead of hand-rolled Meeus formulas, deliberately: these events are only checkable a handful of times a year, so a subtle bug in a hand-rolled implementation could go unnoticed for months, whereas Skyfield's distance-extrema search (`skyfield.searchlib.find_maxima`/`find_minima` over Earth–Moon and Sun–Earth distance) and its built-in `almanac.seasons` event finder are standard, well-tested library code. Sanity-checked against known real-world values on 2026-08-23: Earth perihelion/aphelion landed on 3 Jan/5 Jul as expected, and the next equinox/solstice dates matched published dates for 2026–27. The DE421 kernel (~17MB, public domain) downloads once into `scripts/.ephemeris-cache/` (gitignored) and is cached across workflow runs via `actions/cache` in `fetch-astronomy.yml`, rather than re-pulled from NASA's server daily.

Each cruise ship visit's name links to a **CruiseMapper** details page (specs, deck plans, itinerary) — resolved automatically every fetch against CruiseMapper's own `sitemap-ships.xml` (explicitly crawler-permitted by their `robots.txt`), matched by exact ship name only. No manual ship→ID mapping file: unmatched/ambiguous names (e.g. a generic name that collides with an unrelated vessel in the sitemap) fall back to a Wikipedia search link instead, rather than risk linking the wrong ship. A MarineTraffic tracking URL (built directly from IMO) is also computed into the JSON but not currently rendered — dropped from the table on request to avoid a redundant "Links" column, easy to re-add if wanted later.
